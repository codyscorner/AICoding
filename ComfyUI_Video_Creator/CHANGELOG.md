# Changelog — ComfyUI Video Creator

### Unreleased
- **Icon-only buttons now have a short text label.** Buttons that showed only a symbol (↻, …, 🎲, 🗑 and so on) now read e.g. "↻ Refresh" or "Browse" in regular-weight, regular-size text; their fixed widths were dropped so they size to their label. Covers: ↻ Refresh, 🎲 Random, Browse, 📂 Open, 🗑 Delete, and the video player's ⏸ Pause / ▶ Play, ■ Stop, ⛶ Full screen, ⏮ Prev, ⏭ Next.

### v2.17.1
- **Fix: the model upload/download progress was wrong for any file over 2 GB.** The progress signal carried the byte counts through a 32-bit integer, so an 18.03 GB upload showed "-1911 MB of 855 MB" and a bar stuck near 99%. The counts now arrive intact: real sizes ("9.02 GB of 18.03 GB"), a bar that matches, and a sensible MB/s and time left. The transfer itself was never affected - only the dialog

### v2.17.0
- **Video → Extend: keep track of one set of extensions at a time.** An extension with *Append* ticked saves two files — the short new clip (`…_EXT_<stamp>.mp4`) and the complete video (`…_extended_<stamp>.mp4`) — and both sat in the picker next to every source already extended. A new row under Sort / Show all:
  - **📚 Send to Library** — moves the selected video(s) (the complete ones you want to keep) into the Library folder, inside the active workflow's own folder (`<Library>/<workflow path>/`), after a confirm box listing them and the target. A file already under the Library folder is left alone. Name clashes get `_2`, `_3`; cached thumbnails are dropped and re-made in the new folder; a player showing one of them is closed first. The Library tab and the Extend list refresh, and because the video is now in that workflow's Library folder it counts as the workflow's result (so its source is hidden from the picker by the existing finished-source filter). Also in the right-click menu
  - **Hide** / **Unhide** — take the selected video(s) out of the Extend list by hand, or bring them back (select them with **Show all** ticked, then Unhide). **A source is hidden automatically the moment an extension of it finishes**, so what is left in the list is what you have not extended yet. Kept by file name in `extend_hidden.json` next to the config, so it survives a restart; deleting that file starts a fresh set. Hidden ones count in the `· N done hidden` status
  - **Hide short clips** (on by default, remembered as `extend_hide_clips`) — hides a short `…_EXT_<stamp>` clip when the matching `…_extended_<stamp>` file from the same run is in the same folder. A clip with no complete video beside it (*Append* off, or a failed stitch) is **never** hidden. The status line reads `4 videos · 1 done hidden · 1 short clip hidden`. Show all does not bring the short clips back; untick the box to see them
- Send to Extend (from the Library) still selects a hidden video by un-hiding it, as before
- New module `extend_marks.py` (no Qt): the hidden list and the short-clip matching

### v2.16.0
- **Each workflow has its own Library folder, and "done" is per workflow.** Before, an image counted as finished once *any* workflow had made a video from it, so after running it on workflow 1 it vanished from the picker and could not be tried on workflow 2. Now the Image and Extend pickers hide only the files **the workflow selected on that tab** has already turned into a video that is still in the Library. Switch workflow and the grid re-filters on the spot; the same image stays available for workflow 2 until workflow 2 has made its own. Delete workflow 2's bad video and the image returns for workflow 2 only. "Show all" still shows everything
- **Videos are saved per workflow**: `<Output>/<workflow path without .json>/`, e.g. `Series 1/MiniMax_Makeout_On_Bed_Ext1.json` saves to `<Output>/Series 1/MiniMax_Makeout_On_Bed_Ext1/`. The whole relative path is used because the same file name exists in several workflow subfolders. Stitched extensions land beside their clip, and Library → Reuse Settings still saves back into the video's own folder. Settings → Folders → *Save each workflow's videos in its own folder inside Output* (on by default) turns it off
- **Library has a Workflow selector**: *All workflows*, *Unsorted* (loose in the Library folder) or one workflow's folder. **Follow the active workflow** (on by default) points it at whatever workflow is selected on the Image / Video / Text tab you are on, so you can compare an image against what that workflow already made; picking something else from the list turns following off. A workflow with no runs yet reads "No videos yet for this workflow"
- **🗂 Sort into workflow folders…** (Library → Actions) tidies videos saved loose before this: each workflow's prompt history names the videos it made, so every loose video can be matched to its workflow. It shows the plan first (count per folder, what stays put — videos no history names, claimed by two workflows, or that would overwrite a file) and only moves on Yes. Cached thumbnails travel with the videos, any open player is closed first, and a `_sorted_into_workflow_folders_<time>.txt` list of every move is written to the Library folder. Unmatched videos are left alone
- The Video → Extend picker now lists videos in subfolders too (it points at the Output folder, which now holds the workflow folders). Each folder keeps its own `thumbnails` cache
- Loose videos in the Library root still count as finished for the workflow whose history names them, so nothing reappears before you run the sort

### v2.15.0
- **Delete results from the pod volume once they are downloaded** (new `remote_cleanup.py`). ComfyUI never removes its finished videos from `<ComfyUI>/output` on the network volume, and the volume is billed per GB, so every run left a clip behind. New **Settings → Models → Pod volume cleanup** box: *Delete results from the pod volume after they are downloaded* (**off by default**) and *Output prefix* (default `runpod-slim/ComfyUI/output/`, the output folder inside the bucket). Uses the same S3 connection as model sync
- Safety rules: a file is deleted only if the object is on the volume, the local copy is not empty, and **the local size equals the volume's size** — a truncated download keeps the pod copy and logs why. Only real `output` files (never `temp`/preview), and a path with `..` is refused. After the last file in a run's folder goes, the empty `VideoCreator/<run>` folder is removed too (RunPod leaves directory nodes behind, so it is pruned bottom-up, and only after a listing shows nothing under it). RunPod mode only; a failed cleanup is logged (`Deleted … from the pod volume` / `Pod cleanup: kept …`) and never fails the run. Single-object deletes, because RunPod's bulk delete answers 307

### v2.14.1
- **The video player loads the whole clip into memory before playing it**, so the first play no longer skips and pauses. Streaming an MP4 straight off disk makes the decoder seek between the index and the audio/video chunks; on a hard drive or a just-written file that stutters until the OS has cached it. The player now reads the file sequentially on a background thread (shows "Loading…"), then plays from RAM, and reads the next clip in a playlist while the current one plays so the changeover is smooth too. Files over 1 GB or unreadable ones fall back to streaming. Playing from memory also means the player no longer holds the video file open

Archive / Unarchive on the buttons does the same job for one row or a hundred. Use prompt, Use prompt + settings and Favorite still need exactly one row and grey out otherwise

### v2.13.0
- **Model check & sync before every RunPod run (Settings → Models).** Grown from the Chain Automator's LoRA check, but for *every* model file a workflow names — checkpoints, diffusion models (`unet_name`), VAEs, text encoders (`clip_name*`), CLIP vision, upscalers, ControlNets and LoRAs, keyed by the loader's input name with the class type breaking ties (`CLIPVisionLoader.clip_name` → `clip_vision`, `UpscaleModelLoader.model_name` → `upscale_models`) — and in **both directions**: a file that is local but not on the pod volume is uploaded, one that is on the volume but not local is downloaded into the local models folder, and a file on neither side is reported. The run starts by itself once every copy has been verified by size. New module `model_sync.py`; the pod volume is read through RunPod's S3 API with the same profile / endpoint / quirks as the S3 Browser and the Chain Automator (1800 s read timeout for the server-side multipart merge, 6 retries with backoff, "already landed" check, `.part` download then rename)
  - **What you see:** a `Sync models with the pod?` box listing each file with its folder and size (↑ upload, ↓ download, ✗ nowhere) and the total to move, with **Sync, then run** / **Run without syncing** / **Cancel**; then a progress dialog (file N of M, MB done of total, Cancel after the current file). Everything is echoed to the tab's log. If the volume can't be listed you're asked whether to run anyway rather than being blocked
  - **Multi-select friendly:** requests that arrive together (one per selected image) are held and checked in one pass against one listing, and the pod listings are cached for two minutes, so a 20-image queue costs one check, not twenty. A check against 66 distinct model refs across all 97 workflows takes about 1.5 s
  - **Local lookup is direct**, not a recursive walk: the first version indexed the whole LoRA folder and took three minutes over the share. Each file is now looked up at its own path (both `diffusion_models/` and `unet/`, `text_encoders/` and `clip/`, since ComfyUI treats them as aliases and an install may have either), and only its parent folder is listed to confirm the spelling — the Linux pod is case-sensitive where Windows is not
  - **Local models folder** = Settings → Models → Models folder, or, blank, the parent of the LoRAs folder. ComfyUI's `extra_model_paths.yaml` is not read; point Models folder at that root if your models live elsewhere
  - A transfer counts as "busy", so the pod's idle stop and spend-limit stop wait for it like a run; closing the app cancels a transfer after the current file
  - Settings gains a **Models** tab: enable toggle, Models folder, AWS profile / endpoint / region / bucket / models prefix, **Import from S3 Browser config…** and **Test connection** (lists the pod's model folders and shows the local root it resolved). Config keys `model_check_enabled`, `models_dir`, `s3_profile_name`, `s3_region`, `s3_endpoint_url`, `s3_bucket_name`, `s3_models_prefix`
  - **Build:** boto3/botocore are no longer excluded from the EXE (they were, to keep it small); the EXE grows by roughly 15 MB

### v2.12.0
- **"Start another" falls back to the pod that's already running.** Choosing *start another* in the launch chooser sets the running pod(s) aside for the sweep. If nothing else could be started, the "No pods available" box now says which set-aside pod is still running (with its uptime and spend) and offers **Use <pod>** as the default button, so the app connects to it instead of being left with no pod until a restart. Keep Trying, Switch to Local and Close are unchanged, and the box reads as before when no set-aside pod is still up.
- **Alert sound when a queue finishes.** When 2 or more runs went through back to back and the last one finishes (DONE, nothing left queued), the Alert sound from Settings → RunPod plays — the same sound as "a pod is available" — and the log says `Queue finished (N runs) — alert sound played`. A single run keeps just the usual Windows beep. Respects the "Play alert sound" tick box.
- **Idle stop for RunPod (Settings → RunPod → Idle stop, 10-minute steps, off by default).** When the last run finishes and nothing is queued — the progress bar reads DONE — a countdown starts; if no new run starts before it runs out, the connected pod is stopped. Any new run cancels the countdown, and the next DONE starts it again. The header spend readout shows `idle, stops 03:40` while it counts, and the log says when it arms, cancels and fires. Meant for overnight queues that finish early on a slow GPU, so an expensive pod doesn't sit idle for hours. Applies to any connected pod (opt-in, like Yes on the quit prompt), and only while the app is running.
- **✚ New blank workflow on the Image → Video and Text → Video tabs.** A new button beside ⧉ Clone asks for a name and folder (same dialog as Clone) and creates a workflow from that tab's blank template, with every prompt (positive and negative) emptied, every LoRA switched off and no history, then selects it. LoRA nodes are never removed, so the graph stays valid: rgthree stack slots go to `None`, a single `lora_name` loader keeps its file at strength 0, and the MiniMax Turbo LoRA is left alone (the Turbo toggle owns it). The template file itself is never changed. New `blank_workflow()` in `workflow_tools.py`.
- **Settings → Prompts → New blank workflow** picks the template for each tab from the Workflows folder (`image_blank_template` / `text_blank_template`). With none set, ✚ New says where to set one; a template that has been deleted shows as `(missing)`.
- **Clearer "Stop the pod?" prompt on quit.** It now says the pod is still running and spells out each button: **Yes** stops the pod, then quits (GPU billing ends); **No** quits and leaves the pod running, which keeps billing until it is stopped in the RunPod console, and the pod can be reconnected at the next launch if it is still up. Cancel is unchanged (stay in the app).
- **The quit prompt now asks about any connected pod, not only one this app started.** Picking "use" on a pod in the launch chooser that the app didn't start (the Chain Automator, the console, or a different copy of the app such as the source `run.bat` vs the EXE, which keep separate session files) used to mean closing the app skipped the prompt and left the pod billing silently. Now Yes stops that pod too. The spend limit still never stops a pod the app didn't start on its own — that stays an explicit choice. "Stop pod on exit" in Settings still turns the prompt off entirely.

### v2.4.0

### v1.7.0
- **Start and stop your RunPod pod from inside the app.** Previously the pod had to be woken by hand in the RunPod console before the app was any use in RunPod mode. Now the app talks to RunPod's control plane directly (REST v2, plain `requests` — no new dependency and no change to the build): on launch it offers to start a pod, tries your pods **in priority order**, and uses the first one that actually comes up, writing the proxy URL into the config itself. Only *existing* pods are ever started — nothing is created or terminated, since pods are built and approved by hand.
  - **A resume that "succeeds" isn't necessarily usable.** RunPod pins a stopped pod to the one physical machine it was created on. A pod is only accepted when `status == RUNNING` **and** `gpu.count >= 1` **and** `runtime.gpus` is non-empty; anything else is stopped immediately and the next candidate tried. This is the common failure, not an edge case.
  - **"No pods available" is a normal outcome.** Five stopped pods are five specific machines, not five draws from a pool, so all of them can be busy at once. When the chain is exhausted you're offered a switch to Local rather than shown an error.

  - Progress is logged as `[2/5] trying …` so you can watch it work down the list, and when every pod fails the dialog carries a per-pod breakdown of exactly why each one was rejected.
  - **Double-click a pod in the Settings list** to point the RunPod URL straight at it (the proxy URL is derived from the pod id, so this needs no network call) and switch the mode across.
  - **Live spend readout in the header** — `2h 17m  |  $4.80` — with an optional **session spend limit**. At 80% it warns; at 100% it blocks new runs, lets the current generation finish, then stops the pod. Compute only (storage bills separately), and it needs the app running to act, so it's a safety net rather than a hard cap.
  - **Auto-stop on exit**, and a **crash-recovery check**: the pod the app started is recorded next to the EXE, so if the app dies without its close handler, the next launch spots the still-running pod and offers to stop it.
  - Settings gains a **RunPod pod control** group — fetch your pods, drag them into preference order, set the spend limit, and test the API key (which correctly distinguishes "RunPod is down" from "your key is rejected").

### v1.3.9
- **Fixed: "Append the new clip" failed with `ffmpeg concat failed ... Media type mismatch`.** When both clips carried audio (every MiniMax H3 clip does), the filter graph handed ffmpeg all the video streams and then all the audio streams. `concat` wants each segment's streams together — video, audio, video, audio — so it refused to link the graph and no `_extended.mp4` was written.   - a clip whose aspect ratio differs is fitted inside the first clip's frame and padded with black instead of being stretched
  - audio is resampled to one common format (48 kHz stereo), so clips recorded at different rates still join
  - a clip with no audio track gets matching silence, instead of the whole stitch losing its sound
  - odd frame sizes are rounded down to even, which libx264 requires
  - when ffmpeg still refuses, the error now lists each part's size, fps, duration and audio state plus the filter graph, so the cause is readable from the dialog
